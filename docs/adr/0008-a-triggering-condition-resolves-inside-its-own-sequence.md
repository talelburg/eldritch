# A triggering condition resolves inside its own sequence

The Rules Reference does not describe a triggering condition as a moment with abilities hanging off it. It describes a **sequence**, and puts the condition's own resolution *inside* that sequence — `glossary/Nested_Sequences.md`: *"Each time a triggering condition occurs, the following sequence is followed: 1) execute "when..." effects that interrupt that triggering condition, (2) resolve the triggering condition, and then, (3) execute "after..." effects in response to that triggering condition."* `glossary/At.md` (identical in `glossary/If.md`) adds the middle cell: *"Some abilities have triggering conditions that use the words "at" or "if" instead of specifying "when" or "after," such as "at the end of the round," or "if the Ghoul Priest is defeated." These abilities trigger in between any "when..." abilities and any "after..." abilities with the same triggering condition."*

The engine's timing coordinator walked the three cells but had nowhere to perform step 2: every emit site mutated the board first and *then* emitted, which is why an ability printed **"when"** could only ever resolve after the thing it says it interrupts. So the coordinator frame gains a fourth cursor position — `When → ResolveCondition → At → After` — and `Continuation::EmitEvent` carries it as `step`. The frame is serialized as part of game state, so the step cannot hold a closure: it is dispatched from the timing event's **own value**, through `TimingEvent::condition_resolution`.

Who performs step 2 is an **exhaustive classification**, `ConditionResolution`, with two arms. **Coordinator-owned** means the coordinator resolves the condition between the when and at cells, so the when cell is walked and an interrupt there resolves before the condition's impact lands — what the card prints. **Caller-owned** means the emitting call site still mutates and then emits, so by the time the coordinator runs the condition has already resolved. Exhaustiveness is the enforcement: a new timing event cannot compile without a decision, the discipline ADR 0004 established for classifying continuation frames.

A caller-owned condition's when cell is **not walked**, and an ability declaring interrupt timing on one is **rejected**, naming the condition and this ADR. Resolving that interrupt would resolve it after the thing it was meant to interrupt — a wrong answer dressed as a right one — and dropping it silently is the failure mode this project forbids everywhere else. The reject is what keeps "never silently no-op" true while the migration is in flight.

**The bare milestones are a class, not a list of exceptions.** A condition is a **bare milestone** when nothing about the game state changes as the condition itself resolves: there is no mutation for a caller to have performed ahead of the emit and none for the coordinator to perform, so its resolve step is a documented no-op and its when cell is genuinely safe to walk. The test is not "does nothing happen around it" — plenty happens — but *whose* the teardown is: on a bare milestone the teardown belongs to the frame that emitted the condition, and runs **after the whole sequence** on a resume, rather than between the when and at cells. Six conditions are members, and each earns it the same way:

- **`RoundEnded`**, born coordinator-owned. The round-end teardown, Upkeep → Mythos, runs on the Upkeep anchor's `AfterRoundEnd` resume, not as the condition's impact, which is what act 01109 The Barrier's *"**Objective** - When the round ends, investigators in the hallway may, as a group, spend the requisite number of clues to advance."* has been resolving in all along. Expiring "until the end of the round" lasting effects is the anchor's work too, but it runs just **ahead of** the emit rather than after the sequence: `glossary/Lasting_Effects.md` has a lasting effect expire *"as soon as the timing point specified by its duration is reached. This means that an "until the end of the phase" lasting effect expires before an "at the end of the phase" ability or delayed effect may initiate."* Expiring it as the condition's impact would be too late as well, since the when cell, where The Barrier's objective resolves, runs before the impact (#643).
- **`GameEnd`**, migrated by #720 because Cover Up 01007 prints *"**Forced** - When the game ends, if there are any clues on Cover Up: You suffer 1 mental trauma."* The scenario's ending is *already* structurally after the whole sequence: the `ScenarioEnd` frame advances its own cursor to `Finalize` and emits in tail position, and the ending finishes at the apply boundary — the victory-display scan and the module's `apply_resolution` — once every ability the emit queued has drained. That is exactly why the trauma's interactive acknowledge can span `apply` calls today.
- **`EliminationGameEnd`**, migrated alongside it and for the same card. Rules Reference p.10 Elimination step 0 fires *"when the game ends"* abilities on an eliminated investigator's in-play weaknesses, so Cover Up's one declaration is scanned at both points — the ruling is explicit that it fires here: *"If Roland is eliminated (by being defeated or taking a **resign** action) while Cover Up is in play, Cover Up's **Forced** effect triggers"* (`data/arkhamdb-faq/core/01007.md`). Steps 1–6 run on the re-exposed `Elimination` frame at `EliminationStep::RunSteps`, after another tail-position emit — and so does the sentence that reads most like this condition's own impact. That sentence is step 0's own tail, *"Then, remove those weaknesses from the game."*, which the engine discharges through step 1's threat-area partition rather than at the emit site; it lands after the whole sequence either way. Migrating one of the pair without the other would have made the retag reject the very elimination it was meant to serve.
- **`PhaseStarted`**, born coordinator-owned with the phase-boundary wiring (#697). `Appendix_II_Timing_and_Gameplay.md` step 1.1 calls the beginning of a phase *"an important game milestone that may be referenced in card text"* and describes no mutation, because there is none: what a phase beginning *does* is entirely the driver's — the Mythos round bump and doom, the Enemy phase's hunter movement, each phase's first player window — and every one of those runs on the emitting anchor's own `AfterPhaseStartForced` resume, after the whole sequence. It is the first member born under `ConditionResolution::Caller`'s own rule that *"a new timing event has no legacy emit site to invert, so it is born `Coordinator`"*, and the rule is what decided it: there was nothing to argue about, because there was no prior emit site at all.
- **`CardPlayed`**, born coordinator-owned for Heirloom of Hyperborea 01012's *"\[reaction\] After you play a \[\[Spell\]\] card: Draw 1 card."* (#1048). The condition is the play's **completion**, and its ruling says so: *"This trigger occurs after the Spell card has resolved in full."* (`data/arkhamdb-faq/core/01012.md`). Appendix I step 4 has the card *"regarded as played (and placed in play, or in its owner's discard pile if it's an event)"* simultaneously with that step's completion, so the placement is step 4's own work, finished before the milestone it completes, as Mythos's round bump precedes `PhaseStarted`. It is the one member whose surrounding work runs *before* the emit rather than after, and it could not be otherwise: a placement deferred to the resolve step would leave the card in no zone between the emit and that step, carried only by the event, where elimination's sweep could not find it (ADR 0002). Its when cell is walked, and no corpus card listens there.
- **`TurnBegan`**, born coordinator-owned for On the Lam 01010's *"Fast. Play after your turn begins."* (#778). `glossary/Fast.md` reads a timing point in a Fast card's play instructions as a triggering condition — *"If the instructions specify when/after a timing point, the card may be played as if the described timing point were a triggering condition for playing the card."* — so Appendix II step 2.2, *"Next investigator's turn begins."*, needs a condition for the card to be played after. A turn beginning changes nothing by itself: the rotation that makes the investigator active precedes the emit, as Mythos's round bump precedes `PhaseStarted`, and the post-2.2 player window opens on the Investigation anchor's `AfterTurnBegan` resume, after the whole sequence. Its after cell is that window's first opening only; the window step 2.2.1 returns to after each action is not this condition.

Neither game-end member is an exception to the migration discipline: both had a caller-owned emit site to invert, and inverting it cost nothing precisely because the tail-position emit ADR 0003 already required had left no mutation ahead of the emit to move. What #720 did have to move was a **fork predicate**: `has_weakness_game_end_ability` asked the step-0 scan whether elimination needed its frame at all, and asked it about the `after` cell only. A per-cell scan answering a whole-sequence question drops a retagged ability without a reject to show for it — the elimination takes its inline path and steps 1–6 remove the weakness before anything looks again — which is the same shape as the three `test_support` helpers #723 had to fix, and the reason the predicate now scans every cell.

Every other condition starts caller-owned and flips one at a time, when a card demands its when cell.

**Where each condition stands is in the code, not here.** `TimingEvent::condition_resolution` (`crates/game-core/src/engine/dispatch/emit.rs`) is the exhaustive match, and its arms say what each condition's resolve step does and why the arm fits it. Three rules hold across all of them:

- **Caller-owned costs only the `when` cell.** Every triggering condition walks the coordinator, whoever owns its resolve step, and a pattern pairs with its condition identically in all three cells. There is no per-condition table of which cells a condition supports.
- **A replacement is read between the `when` cell and step 2.** `glossary/Instead.md`: *"A replacement effect is an effect that replaces the resolution of a triggering condition with an alternate means of resolution."* So the coordinator reads the cancellation signal at the resolve step, for every coordinator-owned condition, rather than at the closing window.
- **A prevented condition takes the rest of its sequence with it.** The coordinator abandons the frame rather than advancing the cursor to `At`, and `reaction_windows::withdraw_suppressed_candidates` withdraws every candidate still pending in an open `when`-cell window. Dodge 01023's ruling is the citation (`data/arkhamdb-faq/core/01023.md`): *"If the attacking enemy has a **Forced** ability that says "When attacks" or "After attacks", that ability does not trigger if an attack is Dodged."* Both halves are scoped to coordinator-owned conditions: a caller-owned one has already mutated the board and never walks its `when` cell, so no cancel can sit there.

**One signal, two arms, and the third is #366.** The rules distinguish three ways a condition can be interfered with: a cancel (`glossary/Cancel.md`: *"Cancel abilities interrupt the initiation of an effect, and prevent the effect from initiating."*), a nature-changing `would` replacement, and a replacement that resolves the condition by *other means* without changing its nature. The first two suppress identically, so the engine spends no vocabulary telling them apart — the flag says *prevented*, and both set it. The third does not suppress, and it is **not modelled**: no corpus card wants one, and it is already recorded as **#366** (replace-with-different-impact), under the same norm that keeps DSL primitives out of the engine until two cards want the same pattern. A third modelled case waits on a card that contests it.

**The flag belongs to the condition it prevents.** It is `EmitEventFrame::prevented`, on the cancelled condition's own coordinator frame: `Effect::Cancel` sets it on the topmost `EmitEvent` whose cursor is still at `When`, and the three readers — the timing point's `when`-cell skip, the resolve step, and `withdraw_suppressed_candidates` — each read their own condition's frame. Ward of Protection 01065 is why: *"Cancel that card's revelation effect. Then, take 1 horror."* The horror is dealt through `DamageDealt` and the `DamagePlaced` nested in it, coordinator-owned conditions with resolve steps of their own, while the cancel is live. A single global bool, read and cleared by whichever resolve step ran next, would let the first of them consume Ward's cancel, and the revelation would run anyway. On the frame, a condition emitted after the cancel starts unflagged and resolves, and nothing needs clearing, since the flag leaves with its frame. It is a flag rather than a stack position because positions are not stable while the frame is live: a scenario ending latched mid-sequence (Ward's horror defeating the sole investigator) is inserted at the bottom of the stack (`ContinuationStack::insert_ending_at_bottom`), shifting every frame above it.

## Considered options

**Inverting every emit site at once** — moving every caller-owned condition's mutations behind the coordinator in one change — was rejected on the evidence of ADR 0003. That is the precise manoeuvre four call sites already got wrong: they read a queued emit's `Done` as "nothing happened" and ran their tails *above* the abilities they had just queued, which orphaned agenda 01107's forced end-of-enemy-phase Ghoul movement for a whole scenario (#569; ADR 0003 carries the trace and the printed text). Migrating one condition at a time costs a classification and a reject; migrating them all at once costs a bug class the engine has already paid for once.

**Letting an un-migrated condition's when cell resolve anyway** — collecting the interrupt and firing it after the caller's mutation — was rejected because it is the bug the whole spec exists to fix, only now with the engine's endorsement. An ability that resolves in the wrong cell is harder to notice than one that refuses.

**Storing the resolve step's action on the frame** was rejected on serialization grounds. Continuation frames round-trip through JSON; a fn pointer or closure does not. Recomputing the classification from the event's value at every visit costs one match and keeps the frame plain data.

**Making the classification a default-able trait or a lookup table** was rejected for the same reason ADR 0004 rejected it for continuation frames: a table is a thing a new variant can be forgotten from, and being forgotten is exactly the failure this classification exists to prevent.

## Consequences

**The reject is scaffolding with a terminal condition, and the terminal condition only holds if new events are born coordinator-owned.** When the last condition flips, the caller-owned arm has no members, the when cell is universally available, and the reject is unreachable; at that point the arm, the classification and the reject are deleted together. This is a **commitment**: caller-owned exists to migrate *existing* callers, not to accommodate new ones. A new timing event has no legacy emit site to invert, so there is no reason to reach for it, and reaching for it would make the scaffolding permanent.

**"At" and "if" resolve after the triggering condition's impact lands. This is an interpretation, not a citation.** No vendored source answers it — not the rules, not any per-card ruling, and not the official FAQ, which has now been vendored and checked. `glossary/When.md` pins when as *"the moment immediately after the specified timing point or triggering condition initiates, but before its impact upon the game state resolves"*; `glossary/After.md` pins after as *"the moment immediately after the specified timing point or triggering condition has fully resolved"*; `glossary/At.md` pins at only relative to those two.

The corpus decides it. A sweep of all 159 pack files in the Chapter 1 snapshot (recorded on #693) found **every "at" trigger is a bare milestone** — 269 instances across 18 clause forms, all phase, round, turn or step boundaries — so "at" is never contested by a condition's resolution at all. "If" is contested, in roughly 148 mutating instances dominated by `If <X> is defeated`, and the Core case settles it: **Ghoul Priest 01116 carries 2 victory points**, and act 01110 What Have You Done? prints *"**Objective** - If the Ghoul Priest is Defeated, advance."* with a scenario resolution on its back. If that objective fires when the defeat is *determined* rather than after it has *fully resolved*, the scenario ends with the Ghoul Priest never reaching the victory display, and two earned experience are lost with no recovery. The same shape recurs at The Experiment 02058 and at Silas Bishop 02216 behind act 02200. ADR 0004's Ghoul Priest trace already assumes this reading.

The gap survived the vendoring, which is worth recording, because #672 filed this as a worked example of what a local copy of the official FAQ would let us replace with a citation. It does not. The FAQ's own entry says only what `glossary/At.md` already said — *"(2.2) Timing of "At…" or "If…" abilities … These abilities trigger in between any "when…" abilities and any "after…" abilities with the same triggering condition"* (`data/official-faq/Rulings_and_Clarifications.md`) — and its sequence, *"(1) execute "when…" effects that interrupt that triggering condition, (2) resolve the triggering condition, and then, (3) execute "after…" effects"*, leaves "in between" straddling step 2 rather than landing on one side of it. So the interpretation stands on the corpus evidence above, and the citation gap is in the source rather than in our shelf.

**The gap survives a systematic re-read of the Q&A, not merely the vendoring.** All 145 pairs of the FAQ's *Frequently Asked Questions* section — the part that appears in no other vendored source — have been read against everything the engine implements, and the two candidate pairs were checked directly. **Pair 120** is about a Forced ability *nesting* and needing no player window, which `glossary/Nested_Sequences.md` and `glossary/Ability.md` already cite and which says nothing about cell ordering relative to a condition's impact; **pair 88** is about *attribution* — who counts as having put a location into play — not about trigger timing. `data/official-faq/Rulings_and_Clarifications.md:227` is verbatim identical to `glossary/At.md`: the same "in between", with no anchor to step 2. Settling this needs a new ruling from the publisher, not another pass over the shelf.

**The when cell has an unmodelled internal sub-order.** `glossary/Instead.md`: *"The word "would" is used to define the triggering condition of some abilities, and establishes a higher priority for those abilities than abilities referencing the same triggering condition without the word "would." (For instance, "When X would occur" resolves before "When X occurs.")"* The when cell therefore has two tiers inside it, and the engine implements one. No Core card contests it. Science Building 02056 (Dunwich) will: its *"**Forced** - When you fail a \[willpower\] test in the Science Building: Take 1 damage."* is a bare `when` on the failure Lucky! 01080's *"Play when you would fail a skill test"* names, so Lucky! must resolve first and a test it turns into a success deals no damage. Unmodelled, the Forced resolves first, forced-before-reaction. So this is recorded and not built. A card that contests it needs the sub-tier before it can be implemented correctly.

**The frame's shape is wire-visible, but it carries no compatibility shim, and that was checked rather than assumed.** `Continuation::EmitEvent` reaches every client as part of serialized game state, so the cursor field's rename from `bucket` to `step` looks like a break. It is not one: a coordinator frame exists only in memory, mid-sequence, between two `apply` calls, and the server persists **no game state at all**, only a game's creation inputs plus a `ResolveInput`-only action log, re-running setup and replaying the log on load ([ADR 0022](0022-a-stored-game-is-its-inputs-and-a-checked-log.md)). No persisted artifact can carry the field. A serde alias for the old key was written and then removed: it would have been insurance against a persistence model this project does not have — per-action state snapshots — and a shim nothing can exercise is a claim of compatibility nobody has tested.
