# The engine names the surface a prompt renders on

The board-interactivity pass (#206) rests on one claim: **the client never decides where a control belongs — it reads the anchor the engine attached.** S0 (#535) established that for options by adding `OptionTarget` to `ChoiceOption`, and explicitly rejected the alternative of re-deriving targets from `label` strings. S6 (#541) is where that claim has to hold for everything left over, because there is no flat `.action-bar` behind it to catch what falls through.

Two things did fall through, and both were invisible until the bar was scheduled for deletion.

**The three genuinely-global open-turn actions were not global; they were unnamed.** `TurnAction::EndTurn`, `Resource` and `Draw` all derived `OptionTarget::Global` (`enumerate.rs:141`), so the wire carried three options a client could tell apart only by reading `"End turn"` / `"Gain resource"` / `"Draw"` — the string coupling S0 rejected, arriving through the back door. They are not un-anchored actions. They are actions anchored to surfaces the board did not yet render: a turn control, a resource pool, a player deck. So the anchor vocabulary grows to name them — `TurnControl(InvestigatorId)`, `ResourcePool(InvestigatorId)`, `PlayerDeck(InvestigatorId)`, and `EncounterDeck` for the scenario-wide one — and the client renders those surfaces rather than inferring them.

**A prompt with no options had nowhere to carry an anchor at all.** `InputKind::Confirm` prompts have an empty `options` list by construction, and there are two of them: the Mythos step-1.4 encounter draw (`dispatch/encounter.rs:644`) and the cosmetic skill-test `AcknowledgeOutcome` pause (#478). On the wire they are the same shape — same kind, same empty options, differing only in prose. The bar rendered both as an identical "Confirm" button, which is why the collision never surfaced. Homing one of them on an encounter-deck element requires telling them apart, so **`InputRequest` carries an anchor of its own**, and the anchor is a property of the *prompt*, not only of the options within it. The encounter draw is anchored to `EncounterDeck`; the acknowledge pause is un-anchored and renders on the skill-test result surface; the open-turn menu is anchored to `TurnControl`, which is also how the prompt banner suppresses its `"Choose an action"` text structurally instead of matching on the string.

**"Un-anchored" is spelled `None`, and `OptionTarget::Global` is gone.** `Global`'s own documentation read *"no board anchor"* — a null-object encoding of `Option`, and adding a second nullable field would have put three cases (`None`, `Some(Global)`, `Some(anchor)`) in front of every renderer where two must behave identically. Both `ChoiceOption::target` and `InputRequest::target` are `Option<OptionTarget>`. Removing the variant rather than deprecating it is what makes the migration compiler-verified: 40 sites across 15 files became build errors, so none was missed silently. Some sites read better for it — the Investigate anchor's `map_or(OptionTarget::Global, OptionTarget::Location)` is now the `map` it always meant to be.

**The cost of that shape, accepted knowingly: un-anchored is the silent default.** `ChoiceOption::new(id, label)` and `InputRequest::confirm(text)` produce un-anchored prompts, and `.at(target)` anchors them — one builder idiom for both types, chosen over a required positional argument so the 40 call sites read as prose. A future builder that forgets `.at(…)` therefore compiles, and its option lands in the prompt banner instead of on its card. That failure is caught by tests, not by the type: the engine tests that pin each anchor, and the end-to-end headless test that drives an open turn through the encounter draw to the skill-test acknowledgement without touching anything but the board. Those tests are load-bearing rather than incidental, and deleting one re-opens the hole.

**A surface the engine names by role submits directly; a board entity opens a menu.** The pass's uniform rule is that even a single option opens a context menu, so the player always sees and confirms what they commit to. The four new surfaces are the deliberate exception — End turn, Gain resource, Draw and the encounter draw are buttons that submit on click. The rule exists because a location or an enemy is one entity carrying *several* possible actions, and the entity alone does not say which; a control whose label is `"End turn"` has no such ambiguity, and wrapping it in a one-item menu adds a click to defend against a confusion that cannot occur. The rule reaches **selections** — prompts offering board entities, which is what an anchor disambiguates. A prompt whose options are alternatives printed on one card is not one, and [ADR 0015](0015-a-choice-printed-on-one-card-is-a-decision-not-a-selection.md) exempts it on this paragraph's own rationale. The three per-investigator controls are always present on the active investigator's panel and disabled when no matching option is live, so the panel's shape does not change between phases — layout that jumps as prompts arrive is most of what made the bar worth retiring.

**The last thing that fell through was a choice *inside* an effect, and it fell through by having no source to name.** An `Effect::ChooseOne`'s branches are not board entities — they are alternatives printed on a card — so `step_choose_one` built its options with the un-anchored constructor and every one of them landed in the banner. That was invisible while the only such card was What's Going On?! 01105, whose branches also rendered as their `Debug` form, so there was nothing on the banner worth putting anywhere else. Act 3, What Have You Done? 01110 is the second consumer and settles both halves at once: a branch carries the label it is offered under, and the option is anchored to the card the effect is *printed on*. Nothing in this ADR's principle had to change; what was missing was a value at the dispatch site. The evaluator's `EvalContext` now carries the firing `AbilitySource` beside the `CardInstanceId` it already had — the two are not redundant, because `AbilitySource::instance()` returns `None` for exactly the board sources (the act, the agenda, a location, an enemy) that had no anchor to begin with — and the existing `From<AbilitySource> for OptionTarget` does the rest. **Every dispatch site that holds a source sets it** — the activation path as well as the forced run and the reaction window. It did not start that way: only the two sites already holding a `CandidateSource` set it, and the activation path narrowed its source to a bare `CardInstanceId` on the way into the evaluator, so First Aid 01019's damage-or-horror choice rendered in the banner. #834 collapsed `EvalContext`'s two fields onto the one source, which is what carries an activation's own source through; asserting which *kind* of source a site holds, where it does not know, would still be a silent wrong answer rather than a build error.

That default is the same knowing cost as above, one layer down: an `Effect::ChooseOne` reached from a dispatch site with no source to name renders in the banner and nothing complains. The threaded ones are pinned by tests naming their expected anchor, for the reason this ADR already gives — the type will not catch it.

## Consequences

The board is now the whole input surface, and there is no fallback: an option the engine anchors to a surface the client does not render is unreachable rather than merely misplaced. The prompt banner is the floor that keeps this from being silent — it renders the prompt text for any live request except the open-turn menu, and remains the home for un-anchored options and for Confirm/Pass. Adding a prompt to the engine now carries a client obligation: either anchor it to a surface that exists, or leave it un-anchored and accept the banner.
